Relational file imports append to existing tables and do not infer/create destination schemas. CSV, JSON and XLSX transfers are live verified across PostgreSQL, MySQL, MariaDB, SQLite, SQL Server and Oracle. CSV uses a distinct SQL NULL marker so empty strings remain distinguishable.

Core's direct existing-table transfer has additionally passed all 32 directions among the six relational engines. The live fixture verifies shared integer, Unicode text, NULL, precise decimal/integer, finite floating-point, date, timezone-bearing timestamps, boolean and binary values over bounded keyset pages. That matrix does not cover arbitrary vendor-specific types or every large-LOB route; separate LOB evidence is listed below.

Large-object streaming has current-source evidence for Oracle↔PostgreSQL, Oracle→SQL Server/MySQL/MariaDB, and SQL Server→SQL Server/Oracle/PostgreSQL/MySQL/MariaDB. SQL Server targets require `NVARCHAR(MAX)` / `VARBINARY(MAX)`; MySQL and MariaDB require `LONGTEXT CHARACTER SET utf8mb4` / `LONGBLOB`. Append targets require a primary key. SQLite LOB targets still materialize values; details are in the [Oracle-to-SQL Server report](test-report.md#2026-11-20-oracle-to-sql-server-streamed-lob-transfer), [SQL Server-source report](test-report.md#2026-11-20-sql-server-source-streamed-lob-transfer), and [MySQL-family report](test-report.md#2026-11-20-oracle-to-mysql-and-mariadb-streamed-lob-transfer).

## Spatial row transfer (2026-11-20)

Core transfers matching `geometry` and `geography` columns between PostgreSQL/PostGIS and SQL Server in either direction. Source values are projected to WKB plus SRID, then reconstructed by the destination engine; SQL Server uses `AsBinaryZM` so Z/M ordinates are carried in WKB. An isolated integration passed 3 rows each way with geometry SRID 3857, geography SRID 4326, XY and XYZ samples, NULL spatial values, and two-row keyset pages.

The same current-source integration now passes existing-table `geometry` transfers between PostGIS and MySQL 8.4.13 and MariaDB 11.4.13 in both directions. Each direction checked three XY rows at SRIDs 3857 and 4326 plus NULL, with two-row keyset pages. The EPSG:4326 sample used non-symmetric longitude/latitude coordinates and matched exactly on readback. MySQL WKB calls specify `axis-order=long-lat`; MariaDB uses its documented two-argument WKB constructor. Catalog checks found zero remaining test tables in all four engines. Evidence: [cross-engine spatial transfer](../.cache/gis-roundtrip/spatial-table-transfer-447bcc7235.json). MySQL's WKB constructor and axis-order option are documented in the [MySQL 8.4 reference](https://dev.mysql.com/doc/refman/8.4/en/gis-wkb-functions.html); MariaDB documents [ST_GeomFromWKB](https://mariadb.com/docs/server/reference/sql-statements/geometry-constructors/wkb/st_geomfromwkb).

The current-source Oracle path transfers existing-table `SDO_GEOMETRY` values to and from PostGIS through WKB plus a separately carried SRID. The isolated live run passed four rows per direction, including XY points at SRIDs 3857 and 4326, a NULL geometry, and an Oracle geometry with NULL SRID. A NULL Oracle SRID is represented as PostGIS SRID 0 and restored as NULL. The 2026-11-20 Oracle Z/M rejection and the "no GIS file import/export" statement were superseded by later work; see the dated updates below. This feature does not add spatial-primary-key paging. Evidence: [Oracle/PostGIS spatial transfer](../.cache/gis-roundtrip/spatial-table-transfer-13eb8e2067.json). Oracle documents the WKB conversion functions in [SDO_UTIL](https://docs.oracle.com/en/database/oracle/oracle-database/21/spatl/SDO_UTIL-reference.html) and permits a NULL `SDO_SRID` for an unspecified coordinate system in [SDO_GEOMETRY](https://docs.oracle.com/en/database/oracle/oracle-database/26/spatl/sdo_geometry-object-type.html).

These checks cover only existing-table spatial row transfer. MySQL-family geography data and spatial primary keys remain unsupported, now with explicit live rejection coverage. Dimensional Z/M transfer, SQLite/GeoPackage row transfer, geometry↔geography opt-in conversion, and GIS file import/export scope were extended after 2026-11-20; see the updates below. SQL Server/PostGIS details are in the [test report](test-report.md#2026-11-20-sql-serverpostgis-spatial-row-transfer); MySQL-family details are in [this transfer report](test-report.md#2026-11-20-mysqlmariadb-geometry-row-transfer-with-postgis); Oracle/PostGIS details are in [the Oracle transfer report](test-report.md#2026-11-20-oracle-sdo_geometry-to-postgis-spatial-row-transfer).

### Z/M spatial row transfer and boundary convergence (2026-11-23)

- **Oracle SDO_GEOMETRY ↔ PostGIS** now transfers XYZ, XYM and XYZM geometries in both directions. Oracle `SDO_UTIL.TO_WKBGEOMETRY` loses Z and rejects 4D, so the transfer page query uses `SDO_CS.MAKE_2D` for the structural WKB and carries the original ordinates through `SDO_UTIL.GETVERTICES` JSON; the shared `oracleSdo2dWkbToDimensionalWkb` helper rebuilds ISO dimensional WKB with per-vertex XY verification. The reverse direction normalizes ISO dimensional WKB to the EWKB flags Oracle accepts and reconstructs `SDO_GTYPE` 3001/3301/4401. Verification uses synthetic POINT Z/M/ZM and a LINESTRING Z; SRIDs and NULL geometries still round-trip as before. The helper now also tolerates the one-ULP XY difference introduced by Oracle's `MAKE_2D` coordinate transform. Evidence: [spatial transfer run](../.cache/gis-roundtrip/spatial-table-transfer-730da53b9e.json), [test report](test-report.md#2026-11-23-cross-database-zm-spatial-row-transfer-and-boundary-convergence).
- **SQL Server geometry ↔ PostGIS geometry** was verified with XYM and XYZM points in both directions using `AsBinaryZM()` / `STGeomFromWKB`; Z/M ordinates and SRID are preserved.
- **MySQL / MariaDB** reject dimensional WKB in `ST_GeomFromWKB`. Core now rejects 3D/4D WKB for these targets with an explicit ordinate-loss message instead of leaking the driver's opaque GIS error. Their existing-table spatial row transfer remains XY-only.
- SQL Server and Oracle GIS vector file import/export, previously described here as unimplemented, are implemented and live verified; see [the GIS capability matrix](gis-database-capability-matrix.md) for scope and limits.

### Remaining boundary acceptance (2026-11-23)

- **SQLite/GeoPackage existing-table geometry row transfer** is implemented and live verified with PostGIS in both directions (SRID 3857/4326 + NULL rows, exact WKB and SRS-id readback). The GeoPackage BLOB codec was moved to `@db-studio/shared` so both Core GIS staging and the database layer use it. SpatiaLite-native BLOBs are outside this path.
- **geometry ↔ geography conversion** is available as a deliberate opt-in (`CoreService.transferTableRows({ allowSpatialTypeConversion: true })` / CLI `--allow-spatial-type-conversion`) between PostGIS and SQL Server. Without the flag, type-mismatched mappings are still rejected before any write. The caller must provide a valid geographic SRID; the destination engine enforces its CRS rules. Live verification covered both directions at SRID 4326 plus the rejection without opt-in.
- **MySQL/MariaDB dimensional WKB** and **spatial primary keys** remain deliberately unsupported and now have explicit unit and live acceptance coverage that asserts rejection before destination inserts. A bounded single-page fallback for spatial PKs was not adopted because it would risk silent truncation and unordered, non-resumable transfers.
- Installed-GUI clicking remains environment-blocked (desktop activation returned `False`); startup and window responsiveness were rechecked. A CDP-enabled Electron copy loaded with the **current source build** was used instead and completed a real GUI/IPC PostGIS→SQLite spatial table transfer (2 rows, GeoPackage BLOB and SRID verified), so GUI/IPC behavior is no longer wholly untested — only the signed installer path remains unverified. See [the CDP GUI report](test-report.md#2026-11-23-spatialite-boundary-and-cdp-based-gui-acceptance), [the boundary report](test-report.md#2026-11-23-remaining-gis-boundary-acceptance-sqlite-cross-type-conversion-rejections-gui), [GUI evidence](../.cache/gui-cdp-20261123/acceptance.json) and [spatial transfer evidence](../.cache/gis-roundtrip/spatial-table-transfer-67cb8a23ba.json).
- SpatiaLite-native geometry BLOBs are decoded and encoded in pure JavaScript (no SQLite extension needed), so both GeoPackage BLOBs and SpatiaLite native BLOBs are supported for existing-table row transfer. See [the SpatiaLite acceptance report](test-report.md#2026-11-23-spatialite-native-blob-transfer-and-ai-gui-acceptance).
