Vector file format support is independent of each database's spatial capabilities.

As of 2026-11-22, CLI and desktop GIS imports to MySQL, MariaDB, SQL Server, and Oracle accept a rectangular filter in the source CRS. A live four-database CLI run selected one of two synthetic EPSG:4326 points, returned the expected ID and count, and cleaned both unfiltered and filtered destination tables; see the [mapping and bbox integration evidence](../.cache/gis-roundtrip/gis-vendor-field-mapping-dc7f8c72.json).

MySQL/MariaDB vector import uses a temporary GeoPackage, preserves attribute declarations through portable types, extracts standard WKB and the layer SRS id, then batches inserts through the database adapter. Create/append/overwrite and field renaming/target-type conversion (`string`, `integer`, `integer64`, `real`, `date`, `time`, `datetime`) are supported through CLI and desktop GIS routes. Overwrite imports into a staging table and swaps it into place only after row counts match; the prior table is retained if staging fails. Source-coordinate rectangular filtering and explicit GDAL `-makevalid` repair during staging are supported. A four-engine live smoke verified repaired geometry after reading it back from each database and exporting to GeoPackage; MakeValid can alter geometry type, produce empty/collapsed output, or change M values. UTF-8 tail repair is supported for standalone Shapefiles when UTF-8 is explicitly selected; it repairs only incomplete terminal code points in a temporary copy, leaves source files unchanged, and rejects ZIP-internal Shapefiles and other formats. Spatial-index availability and its per-engine constraints are listed in the dated update below. Append commits batches independently, so an error after earlier batches can leave those rows committed and is reported with the committed count.

MySQL/MariaDB vector export streams one spatial column and its attributes into a temporary GeoPackage, then uses GDAL to write the selected vector format. It rejects tables with multiple geometry columns or mixed SRIDs. MySQL SRS metadata is used when available. If the server does not expose a CRS definition, export requires an explicit source CRS and reports that assignment. Export supports attribute mapping/type casting, target CRS, GDAL creation options, and source-CRS rectangular filtering. For MySQL geographic SRIDs, WKB is explicitly requested in `axis-order=long-lat` so GeoPackage XY and bbox coordinates retain traditional longitude/latitude order; see the [MySQL WKB conversion reference](https://dev.mysql.com/doc/refman/8.4/en/gis-format-conversion-functions.html).

As of 2026-11-22, Core and CLI source-CRS bbox export is verified on PostGIS, MySQL, MariaDB, SQL Server, and Oracle. PostGIS applies GDAL `-spat` directly to the database export. The other four engines stage all source rows into a temporary GeoPackage in bounded batches, then GDAL applies the bbox when writing the requested output; this bounds application memory but does not reduce source database scan or transfer volume. The desktop bbox field and IPC bridge compile and pass renderer tests, but installed-GUI clicks remain unverified. See the [five-engine bbox export test](test-report.md#2026-11-22-gis-source-crs-bbox-export-across-five-databases).

SQL Server and Oracle GIS imports accept the same field mappings. Mapping supports field renaming and `string`, `integer`, `integer64`, `real`, `date`, `time`, and `datetime` target types. The four-engine live smoke verified date and datetime values including milliseconds. Oracle does not have a standalone TIME type, so mapped time values are stored as `VARCHAR2(32)` text. Oracle `DATE` and `TIMESTAMP(3)` imports explicitly parse ISO local date/time strings instead of depending on session NLS formats; unsupported string layouts are rejected. SQL Server import supports both `geometry` and `geography`; geography requires a non-zero SRID whose catalog definition is geographic. Source-coordinate rectangular filtering and explicit GDAL MakeValid repair during staging are supported through Core and CLI; the desktop import option is wired but installed GUI clicks remain unverified. The live smoke verified a repaired bowtie after database readback and GeoPackage export for all four engines. UTF-8 tail repair is supported for standalone Shapefiles when UTF-8 is explicitly selected; it repairs only incomplete terminal code points in a temporary copy, leaves source files unchanged, and rejects ZIP-internal Shapefiles and other formats. Spatial-index availability and its per-engine constraints are listed in the dated update below. Oracle imports XY only, maps an unknown GeoPackage SRID to a NULL SDO SRID, and rejects Z/M before Oracle conversion; export also prechecks `SDO_GTYPE` and rejects non-XY values before `TO_WKBGEOMETRY`. Oracle export requires one spatial column and one SRID; without the spatial-index opt-in, imports do not register `USER_SDO_GEOM_METADATA`. Oracle and SQL Server append commit each batch independently, so rows committed before a later failing batch can remain and are reported. Existing-table cross-engine spatial transfer remains independent of file import/export and spatial-primary-key paging. Oracle NULL SRID maps to PostGIS SRID 0 during row transfer and back. SQLite spatial row transfer, MySQL-family geography and Z/M, and geometry↔geography conversion remain unsupported or unverified. Oracle file evidence is [Oracle SDO GIS file import/export](test-report.md#2026-11-22-oracle-sdo_geometry-gis-file-import-and-export); mapping evidence is [four-engine GIS import field mapping](test-report.md#2026-11-22-gis-import-field-mapping-across-four-database-engines); other live evidence is in [SQL Server/PostGIS](test-report.md#2026-11-20-sql-serverpostgis-spatial-row-transfer), [SQL Server vector import](test-report.md#2026-11-21-sql-server-gis-vector-import), [SQL Server vector export](test-report.md#2026-11-21-sql-server-gis-vector-export), [MySQL/MariaDB/PostGIS](test-report.md#2026-11-20-mysqlmariadb-geometry-row-transfer-with-postgis), [Oracle/PostGIS](test-report.md#2026-11-20-oracle-sdo_geometry-to-postgis-spatial-row-transfer), [MySQL/MariaDB vector import](test-report.md#2026-11-21-mysql-and-mariadb-gis-vector-import), and [MySQL/MariaDB vector export](test-report.md#2026-11-21-mysql-and-mariadb-gis-vector-export).

Update (2026-11-22, Oracle): statements above that Oracle spatial metadata/index creation is unavailable were superseded for Oracle create-mode imports by the opt-in described in the [Oracle spatial-index test report](test-report.md#2026-11-22-oracle-sdo-spatial-index-opt-in). See the later cross-engine update for current scope.

Update (2026-11-22, cross-engine): MySQL and MariaDB create/overwrite imports can opt in to a `SPATIAL` R-tree index. They require a positive layer SRID and every feature must have a non-NULL geometry. MySQL uses its native `SRID` column restriction; MariaDB records `REF_SYSTEM_ID` metadata and adds an enforced `CHECK (ST_SRID(geom) = n)` because its SRID metadata alone does not reject mismatched geometry values. SQL Server create/overwrite imports can opt in for geometry or geography: the staged integer GeoPackage feature ID becomes a clustered primary key, geometry uses a padded staged-extent bounding box, and geography uses `GEOGRAPHY_AUTO_GRID`. Indexed append now reuses the destination index for all three engines after preflight: MySQL checks native column SRID/NOT NULL; MariaDB checks its enforced SRID CHECK/NOT NULL; SQL Server checks the enabled SPATIAL index and matching clustered key, plus the existing geometry bounding box when present. MySQL-family NULL geometries and SQL Server geometry features outside a finite index bbox are rejected before writes. Core/CLI acceptance passed on isolated MySQL 8.4, MariaDB 11.4, and SQL Server 2022. Oracle also supports indexed append only into an existing VALID index when SRID, X/Y metadata and source extent pass validation. See [initial index report](test-report.md#2026-11-22-mysql-mariadb-and-sql-server-spatial-index-opt-in), [indexed overwrite report](test-report.md#2026-11-22-mysqlmariadb-and-sql-server-indexed-overwrite-acceptance), [Oracle append/overwrite report](test-report.md#2026-11-22-oracle-indexed-append-and-overwrite-acceptance), and [cross-engine indexed append report](test-report.md#2026-11-22-mysqlmariadb-and-sql-server-indexed-append-acceptance). Installed GUI clicks remain unverified.

Update (2026-11-22, Oracle Z/M import): the older statement above that Oracle file imports reject Z/M is superseded. Core import now normalizes standard ISO dimensional WKB types 1–7 into Oracle-accepted EWKB while preserving XY, XYZ, XYM, or XYZM coordinates. Core and CLI synthetic imports read back the expected SDO_GTYPE and ordinates. Optional Oracle spatial indexing remains XY-only and validates the entire staged layer before any destination writes. See the [Oracle dimensional import test](test-report.md#2026-11-22-oracle-sdo-geometry-zm-gis-file-import).

Update (2026-11-23, remaining boundaries): SQLite/GeoPackage existing-table geometry row transfer to/from PostGIS is implemented and live verified using GeoPackage geometry BLOBs; the codec now lives in `@db-studio/shared`. SpatiaLite-native geometry BLOBs are not interpreted by this path. PostGIS↔SQL Server geometry↔geography conversion is available as an explicit opt-in with caller-validated geographic SRID. MySQL/MariaDB dimensional WKB, spatial primary keys, and cross-type transfers without opt-in are deliberately rejected with acceptance coverage. SpatiaLite-native BLOBs are now decoded/encoded in pure JavaScript and row transfer was verified against GDAL-generated fixtures. Installed-GUI activation remains environment-blocked, but a CDP-enabled Electron copy with the current build completed real GUI PostGIS→SQLite spatial transfer and AI SQL generation; see [the SpatiaLite+AI report](test-report.md#2026-11-23-spatialite-native-blob-transfer-and-ai-gui-acceptance) and [the CDP GUI report](test-report.md#2026-11-23-spatialite-boundary-and-cdp-based-gui-acceptance).

Update (2026-11-23, Z/M cross-database row transfer): the statements above that Oracle existing-table spatial transfer is XY-only are superseded. Oracle SDO_GEOMETRY ↔ PostGIS row transfer now carries XYZ/XYM/XYZM in both directions by combining a `MAKE_2D` structural WKB with `GETVERTICES` ordinates, then rebuilding ISO dimensional WKB via the shared reconstruction helper. SQL Server geometry ↔ PostGIS geometry was verified with XYM/XYZM points. MySQL and MariaDB remain XY-only and now reject dimensional WKB explicitly. The reconstruction helper was moved to `@db-studio/shared` so both GIS export and row transfer reuse it, and it tolerates the one-ULP XY difference introduced by Oracle's `MAKE_2D`. See [the Z/M transfer report](test-report.md#2026-11-23-cross-database-zm-spatial-row-transfer-and-boundary-convergence) and the [database capability matrix](database-capability-matrix.md#zm-spatial-row-transfer-and-boundary-convergence-2026-11-23).
