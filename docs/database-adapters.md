Adapters expose database-specific capability declarations and preserve dialect differences. Driver installation and real integration results will be recorded per adapter before marking it complete.

All relational adapters expose table-column metadata and table transfer through Core Service. CSV, JSON and XLSX imports append to existing base tables inside a transaction and roll back the batch on failure. XLSX import/export is implemented through shared Core, CLI and desktop paths; PostgreSQL, MySQL, MariaDB, SQLite, SQL Server and Oracle live integrations verify its round trip. Imports do not infer or create destination table schemas, and large table exports currently load the result into memory.

Direct cross-database transfer through Core Service is live verified in all 30 directions among the six relational engines (15 pairs), using existing destination tables and two-row keyset pages. The common fixture verifies integer primary keys, Unicode text, nullable text, `DECIMAL(16,4)` values and four-byte binary payloads (including zero and high-bit bytes). SQL Server binds byte arrays as `VARBINARY(MAX)`; Oracle binds byte arrays as `BUFFER`/RAW. Core and desktop now support explicit source-to-target column mappings and omitting source columns; skipped non-key columns are excluded from each source page query. In the 2026-11-13 integration run, the original 30 directions passed and custom renamed-column mappings passed in both PostgreSQL→SQLite and SQLite→PostgreSQL directions, with all expected values checked and temporary tables removed. The mapped path also has SQLite Core regression coverage. Installed-GUI interaction remains unverified. Values are still passed through the source driver without type conversion; vendor-specific types, large LOB streaming, timezone semantics, arbitrary precision, and general type conversion remain open.

Excel input reads the first worksheet, uses the first row as unique, non-empty column names, preserves numbers/booleans/dates/nulls, and applies 50 MiB compressed-file, 128 MiB actual ZIP-expanded-size, 4,096 ZIP-entry, 100,000 data-row, 2,048 column, and 1,000,000 cell-work limits. Before ExcelJS loads the workbook, the ZIP preflight checks archive boundaries and streams each stored/deflate entry through a bounded inflater, verifying actual expanded bytes against both the directory metadata and aggregate limit. Multi-disk, ZIP64, encrypted, and other compression-method archives are rejected. The preflight runs a separate bounded decompression pass before ExcelJS parses the workbook, so accepted archives are decompressed twice. It appends to an existing table. CSV/JSON/XLSX paths are live verified for PostgreSQL, MySQL, MariaDB, SQLite, SQL Server and Oracle. Excel exports query results with a header row and the same row/column/cell-work ceilings.

MongoDB uses its own `MongoDocumentAdapter` and `MongoDocumentService`; it is not coerced into SQL tables. Extended JSON preserves BSON `ObjectId` values across import/export. GeoJSON Geometry/Feature/FeatureCollection conversion, configurable geometry paths, index metadata, `2dsphere` index creation, and native `$geoWithin`/`$geoIntersects` filtering are available. The desktop page can inspect/create `2dsphere` indexes and accepts MongoDB-native spatial operators in Filter. MongoDB GUI URIs are encrypted with OS-backed storage (current-user DPAPI on Windows, Electron safeStorage on other platforms) and are not returned to the renderer.

SQLite is implemented with Node's built-in synchronous SQLite API to avoid a native addon dependency. The project minimum is Node 22.13 because that release made `node:sqlite` available without an experimental startup flag. The API is still marked release candidate in the current Node documentation and executes synchronously, so long-running SQLite statements can block the process. See the [Node.js SQLite documentation](https://nodejs.org/api/sqlite.html).
